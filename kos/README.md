Готовые блоки для автоматизации полётов в Kerbal Space Program через
[kOS](https://github.com/KSP-KOS/KOS). Не «скрипт на один запуск», а набор
модулей: подъём, узлы манёвра, наука, телеметрия, индикация — каждый в своём
файле. Файл миссии содержит только цифры цели и порядок шагов.

Всё проверено в полёте на сборке [«Оператор»](https://kerbal.ru/Operator),
KSP 1.12.5, kOS 1.6.0.1. Подробные разборы — в вики:
[библиотека модулей](https://kerbal.ru/Operator/wiki/kos-biblioteka.html) ·
[разбор ошибок вывода на орбиту](https://kerbal.ru/Operator/wiki/kos-vyvod-orbita.html) ·
[отладка и лимиты](https://kerbal.ru/Operator/wiki/kos-otladka.html) ·
[интерфейс и графика](https://kerbal.ru/Operator/wiki/kos-interfeys.html) ·
[управление по telnet](https://kerbal.ru/Operator/wiki/kos-telnet.html)

## Установка

Скопируй содержимое в архив kOS — это папка `Ships/Script/` в каталоге игры:

```bash
cp -r kos/lib kos/missions kos/check kos/boot "<KSP>/Ships/Script/"
```

Проверь, что всё компилируется, прямо на стартовом столе:

```
RUNPATH("0:/check/libcheck.ks").
```

Полёт:

```
RUNPATH("0:/missions/dalnyak.ks").
```

> **Имена файлов только строчными.** На macOS и Linux kOS не найдёт файл,
> если регистр не совпадает. Поэтому папка называется `kos`, а не `kOS`.

## Что внутри

```
lib/          модули механики
missions/     файлы миссий: только цель и порядок
check/        прогон библиотеки без запуска двигателей
boot/         загрузочные файлы отдельных процессоров (не файлы миссий)
tools/        telnet-клиент для управления снаружи игры
```

### Загрузочные файлы (`boot/`)

Не путать с `missions/`. Файл миссии запускает игрок командой `RUNPATH`.
Загрузочный файл ставится на **процессор конкретной детали** в VAB —
правый клик по CPU → Boot File — и выполняется сам, без команды игрока,
как только у процессора появляется питание. Нужен там, где переключать
фокус на аппарат не вариант — например, спутник, который должен раскрыть
панели и антенну сразу после отстыковки, пока шина летит дальше.

Это не нарушает правило «kOS работает только на аппарате в фокусе»
([[flot]]): дело не в фокусе, а в физической дальности 2,5 км — сразу
после отделения оба аппарата ещё рядом, и физика считается для обоих.

`sat-boot.ks` — под спутники Дальняк-Мун: раскрывает панели и антенну,
проверяет остаток монотоплива. Антенну ни на что не наводит — связь тут
стоковый CommNet, дальность решает мощность детали, а не направление,
см. [[svyaz-osnovy]].

### Миссия одной строкой

Говоришь целевую орбиту — остальное `mission.ks` считает сам:

```kos
RUNONCEPATH("0:/lib/mission.ks").

SET s TO m_defaults().
SET s["name"] TO "Спутник-2".
SET s["ap"]  TO 7867078.   // апоцентр, м
SET s["pe"]  TO 3331362.   // перицентр, м (убери — будет круговая)
SET s["inc"] TO 20.1.      // наклонение, °
SET s["lan"] TO 250.8.     // долгота узла, ° (-1 = не ждать окна)
SET s["aop"] TO 29.6.      // аргумент перицентра, ° (-1 = не важен)

m_orbit(s).
```

Что решается автоматически:

| Что | Как |
|---|---|
| Азимут пуска | из наклонения, с поправкой на вращение планеты |
| Ждать ли окно | если задана долгота узла |
| Схема выведения | **без** аргумента перицентра — один совмещённый прожиг; **с** ним — круговая парковка, ожидание нужной точки витка и прожиг именно там |
| Подъём перицентра | только если он реально ниже цели |
| Порядок апсид | перепутал `ap` и `pe` местами — поменяет молча |

Готовые примеры: `missions/dalnyak.ks` (без аргумента перицентра) и
`missions/survey2.ks` (с ним). Оба — по шестнадцать строк, из них половина
комментарии.

### Дальний вылет одной спецификацией

Тот же принцип, но для перелёта к другому телу и выпуска нескольких
лендеров, — `ds_run(s)` из `lib/deepspace.ks`:

```kos
RUNONCEPATH("0:/lib/deepspace.ks").

SET s TO ds_defaults().
SET s["body"]     TO MUN.
SET s["parkAlt"]  TO 100000.      // рабочая орбита созвездия
SET s["mapAlt"]   TO 0.           // не поднимаемся — шина садится сама
SET s["landers"]  TO LIST("sat-1", "sat-2", "sat-3", "sat-4").
SET s["selfLand"] TO TRUE.        // шина сама садится после развода спутников
SET s["sci"]      TO TRUE.

ds_run(s).
```

`landers` — общее имя для всего, что отделяется по метке декаплера: лендеры,
которые садятся сами, или спутники, которые остаются на орбите — механика
одна, `selfLand` решает, что дальше делает сама шина.

Готовый пример — `missions/dalnyak-mun.ks`. Архитектура и цифры разобраны
в вики: [миссия на Мун](https://kerbal.ru/Operator/wiki/missiya-mun.html) и
[автоматизация запуска](https://kerbal.ru/Operator/wiki/kos-avtomatizaciya.html).

### План: телеметрия + чекеры + Δv-бюджет одной спецификацией

Тот же принцип, что у `ds_run`: логика — в `q_plan(spec)` из `lib/audit.ks`,
файл на конкретный корабль — только параметры. Ничего не жжёт и не ставит
узлов манёвра, только читает `SHIP` и считает.

```
RUNPATH("0:/check/dalnyak-mun-plan.ks").
```

Что внутри файла — не логика, а спецификация:

```kos
SET spec TO LEXICON(
  "tasks", LIST(
    LEXICON("title", "SCANsat: высотометрия", "items", q_taskScanAltimetry()),
    LEXICON("title", "Созвездие: 4 спутника", "items", q_taskConstellation(4, "sat-"))
  ),
  "budget", LIST(
    LEXICON("label", "перелёт к телу", "dv", 856, "optional", FALSE),
    LEXICON("label", "смена плоскости (опция)", "dv", 770, "optional", TRUE)
  )
).
q_plan(spec).
```

Общие блоки — в `lib/audit.ks`: `q_hasPart`, `q_countTag`, `q_bodyChecklist`,
заготовки под типовые задачи (`q_taskScanAltimetry`, `q_taskConstellation`
и т.д.), `q_shipReport`/`q_dvBudget`/`q_liveTransfer` под саму спецификацию
плана. Новый корабль — новый `spec`, не новый скрипт с нуля.

## Правила, на которых всё держится

Они выведены из отказов, а не из теории — каждое стоило потерянной ракеты.

1. **Префиксы имён.** В kOS одно глобальное пространство имён. Каждый модуль
   помечает свои функции буквой: `u_`, `c_`, `s_`, `o_`, `a_`, `d_`, `t_`, `h_`.
2. **`GLOBAL FUNCTION`**, иначе функция не видна вызывающему файлу.
3. **Никаких побочных действий при загрузке.** Модуль только объявляет.
4. **Настройки — лексиконом**, обработчики — ссылками на функции через `@`.
   Модуль не должен знать ничего о конкретной миссии.
5. **Один владелец у объекта.** Раз `o_burn` снимает узел через `REMOVE`,
   он же его и вешает через `ADD`. Иначе `nd:DELTAV` падает с
   «Must attach node first» — и падает уже в полёте, компиляция это не ловит.
6. **Имена, занятые встроенными.** `r`, `v`, `q`, `alt`, `path`, `time`, `node`,
   `stage`, `config` и десятки других объявить нельзя. Проверяй прогоном
   `check/libcheck.ks` до пуска.

## Что уже отработало в полёте

- Подъём с ограничением угла атаки — аэродинамически неустойчивая ракета
  (оперение выше центра масс) выведена без единого срыва.
- Расписание тангажа вместо следования за потоком — экономия около 1500 м/с
  на скруглении орбиты.
- Автостейджер по отсутствию живых двигателей — переживает ступени-переходники,
  где двигателя нет вообще.
- Ожидание окна под долготу восходящего узла — модель, выведенная из
  телеметрии собственного полёта, попала в 311° с точностью 0,03°.
- Сбор науки на каждом рубеже с передачей только в вакууме: складная антенна
  раскрывается сама при передаче и ломается от напора в атмосфере.
- Фильтр по ценности: перед передачей смотрим `TRANSMITVALUE`, и если субъект
  уже выбран до предела — данные сбрасываем, а не жжём на них электричество.
- Ожидание нужной точки витка под аргумент перицентра — попали в 29,50°
  при заказанных 29,6°.

## Управление снаружи игры

`tools/kos.py` — telnet-клиент к встроенному серверу kOS. Обычный `nc` не
годится: kOS требует RFC 1073 (размер окна) и RFC 1091 (тип терминала), а без
учёта уже согласованных опций стороны уходят в бесконечные переговоры.

```bash
python3 kos/tools/kos.py 'PRINT SHIP:APOAPSIS.'
python3 kos/tools/kos.py 'RUNPATH("0:/check/libcheck.ks").'
```

Включается в игре: панель kOS → TELNET, порт 5410 на `127.0.0.1`.

> Пока программа работает, в терминал писать нельзя — kOS воспримет ввод как
> прерывание и остановит её.

## Как участвовать

Библиотека открыта, и её есть куда растить. Что напрашивается:

- стыковка по портам — сейчас рандеву подводит на дистанцию, причаливание за игроком (`rendezvous.ks`);
- фазировка созвездия: развести N аппаратов по орбите равномерно;
- прицельная посадка в заданную точку/биом, а не «где получится» после `l_go`;
- пульт на виджетах kOS для ручных операций.

Перелёт к другому телу (`transfer.ks`), посадка на тело без атмосферы
(`land.ks`) и дальний вылет одной спецификацией (`deepspace.ks`) уже есть,
но **не проверены в полёте** — прогнаны только через `check/libcheck.ks`
на арифметике. Первая живая цель — «Дальняк-Мун».

Правила простые: модуль в свой файл, префикс в именах, никаких побочных
действий при загрузке, проверка через `check/libcheck.ks` перед отправкой.
Присылай пулл-реквест или заводи
[issue](https://github.com/plagness/kerbal.ru/issues).

Если поймал грабли — опиши их в описании изменений. Половина ценности этой
библиотеки не в коде, а в списке того, обо что мы уже споткнулись.
